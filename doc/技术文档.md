# P2PChat 技术文档

本文档描述 P2PChat 的架构设计、核心流程、数据结构与关键实现细节，供二次开发与维护参考。

## 1. 总体架构

P2PChat 是一个**单文件纯前端应用**（`index.html`），所有 HTML、CSS、JavaScript 内联在一个文件中，无外部依赖、无构建步骤、无后端服务。

### 1.1 技术选型

| 能力 | 方案 |
|------|------|
| 传输通道 | WebRTC `DataChannel`（有序可靠模式） |
| 加密 | DTLS（WebRTC 强制，端到端） |
| 信令 | 手动复制粘贴连接码（base64 编码的 JSON） |
| NAT 穿透 | 始终启用国内公共 STUN 获取 srflx 反射地址，绕过 Chrome mDNS 混淆；host 候选作补充。仍需双方在同一局域网或均具公网 IP（STUN 不能穿越对称型 NAT，见 §1.4） |
| 持久化 | `localStorage` 自动保存 + JSON 文件导出/导入 |
| UI | 原生 DOM + 响应式 CSS（桌面双栏 / 移动单栏） |

### 1.2 为什么是「手动信令」

浏览器安全沙箱有两点根本限制：
1. 无法用 IP 建立原始 TCP/UDP 连接；
2. 无法监听入站连接。

因此「输入 IP 即直连」在纯前端不可行。WebRTC 是唯一可行的浏览器 P2P 技术，但其建立连接需要一次信令交换（交换 SDP offer/answer）。在无后端的前提下，采用**手动复制粘贴连接码**完成信令。

### 1.3 固有限制

WebRTC 的 SDP（含 DTLS 指纹、ICE ufrag/pwd）是**每次会话临时生成**的，无法跨会话复用。因此：
- 已保存的联系人**无法凭存储的 IP 自动重连**；
- 每次重新连接仍需双方**重新交换一次连接码**。

联系人列表中的 IP/备注仅用于识别与整理，不用于「拨号」。

### 1.4 候选类型与 mDNS

ICE 连通依赖候选（candidate）：

| 候选 | 来源 | 受 mDNS 影响 |
|------|------|--------------|
| `host` | 本机网卡 IP | 是，被混淆为 `*.local` |
| `srflx` | STUN 反射地址 | 否 |
| `relay` | TURN 中继 | 否 |

仅直连模式 `iceServers: []`，ICE 只能收集 `host` 候选。Chrome 默认开启 mDNS 混淆，将 host 候选改写为 `*.local`，对端在不同子网 / 组播受限 / 不同浏览器实例时常解析失败，导致连接**静默失败**（ICE 不报错，只是连不通）。因此仅直连模式下，**关闭 mDNS 混淆是连通前提**（详见 §8）。有 STUN 时此问题不存在——`srflx` 候选为 STUN 返回的真实地址，不依赖 host，故 mDNS 开关与否均能连通。

> **STUN 辅助始终启用**：较新 Chrome 版本已收紧/移除 `chrome://flags/#enable-webrtc-hide-local-ips-with-mdns` 开关，用户可能无法手动关闭 mDNS。因此 `newPC()` 始终填入公共 STUN，ICE 即可收集 `srflx` 候选绕过 mDNS。仅在建连阶段联系 STUN 获取反射地址，消息仍端到端加密、不经过 STUN。`collectMyIps()` 探测本机地址时同样启用 STUN，以收集 `srflx` 反射地址用于本机地址面板展示（本机真实 IP 被隐藏时显示 STUN 反射的公网地址并标注）。
>
> **IPv6 srflx 兜底**：国内公共 STUN（`stun.miwifi.com` / `stun.qq.com` / `stun.chat.bilibili.com`）仅有 A 记录，只能反射 IPv4；mDNS 同样会隐藏公网 IPv6 的 host 候选，导致 IPv6 无 srflx 兜底而无法直连。为此补充 Cloudflare STUN（`stun.cloudflare.com`，有 AAAA 记录，支持 IPv6 反射且国内可达）作为首选 IPv6 候选，Google STUN（`stun.l.google.com`，同样有 AAAA）作为候补：浏览器通过 IPv6 向这些 STUN 请求可产生 IPv6 `srflx` 候选，恢复 mDNS 隐藏下的 IPv6 直连。Google STUN 国内可能不可达，不可达时退回 IPv4（国内 STUN 及 Cloudflare 仍兜底），不影响连接。WebRTC 对所有 STUN 并发请求，互不依赖。

## 2. 连接流程（三步手动信令）

为简化交互，**关闭 trickle ICE**，等 ICE 收集完成后读取完整 `localDescription`（含全部候选）再编码，使每方只需复制一段文本。

> **生成连接码的等待提示**：启用 STUN 后，`waitIceComplete` 需等 STUN 服务器返回 `srflx` 候选（网络往返），生成邀请码/应答码会有短暂延迟。`startInvite` 点击后立即弹出对话框显示 spinner +「正在生成邀请码…」；`acceptOffer` 点击后立即在应答码框显示「正在生成应答码…」并 toast。避免用户以为点击无反应。`ips` 字段改用 `extractIpsFromPc(pc)` 复用已收集候选，省去额外的 STUN 探测往返。

```
邀请方 A                         被邀方 B
─────────                       ─────────
createDataChannel('chat')
createOffer + setLocalDescription
wait iceGatheringState==='complete'
生成【邀请码】 ────────────────▶ 粘贴邀请码
                                  setRemoteDescription(offer)
                                  ondatachannel 监听
                                  createAnswer + setLocalDescription
                                  wait ICE complete
                  ◀────────────  生成【应答码】
粘贴应答码
setRemoteDescription(answer)
                ▼ ICE 连通 / DTLS 握手 ▼
            DataChannel open，互发 hello
                ▼ 双向加密聊天 ▼
```

### 连接码格式

```
base64( JSON{ type, sdp, identity, ips } )
```

- `type`：`'offer'` 或 `'answer'`
- `sdp`：`RTCSessionDescription`（含所有 ICE 候选）
- `identity`：`{ id, name }`，本机身份
- `ips`：本机真实 IP 字符串数组（host v4/v6 + STUN srflx 反射地址，排除 `*.local`/`0.0.0.0`/`::`），由 `extractIpsFromPc(pc)` 从已收集的 `localDescription` 提取（复用握手 PC 候选，省一次 STUN 往返）。用于对端在 mDNS 混淆下 `getStats()` 仅拿到 `*.local` 时回退显示真实 IP（`ipType='signal'`）。**不参与连通性**（在 non-trickle 全候选架构下，真实候选 SDP 已含，故不做候选注入）。

编码采用 `btoa(unescape(encodeURIComponent(...)))` 以兼容中文等 UTF-8 字符；解码对称。

### 身份解析时机

- **被邀方**：邀请码中已含邀请方 `identity`，`ondatachannel` 时即可知对端身份，通道打开后立即登记联系人。
- **邀请方**：应答码中虽含被邀方身份，但邀请方在 `finalizeOffer` 阶段未解析它；邀请方需等对端通过 DataChannel 发来 `hello` 消息才能确认身份。故邀请方通道打开后先「等待对端身份」，收到 `hello` 再登记。

## 3. 数据结构

### 3.1 持久化结构（`localStorage` key: `ipvchat_data`）

```js
{
  version: 4,
  identity: { id, name },                 // 本机身份
  contacts: [
    { id, name, peerName, ip, ipType, lastSeen, note, nameSet, peerIps? }
  ],
  messages: { [contactId]: [ { ts, dir, text } | { ts, dir, file:{fid,name,size} } ] },
  settings: {},                            // STUN 始终启用，无运行时开关
  unread: { [contactId]: number }          // 未读消息计数
}
```

字段说明：
- `identity.id`：随机生成的本机唯一标识，随连接码发送给对端，作为联系人去重键。
- `contacts[].id`：对端身份 id（非 IP），用于匹配连接。
- `contacts[].peerName`：对端账号用户名，每次连接经 `hello` 同步更新。
- `contacts[].name`：本机自定义备注名（仅 `nameSet=true` 时有效）。
- `contacts[].nameSet`：是否已设置备注；为 `true` 时显示为「备注（用户名）」，否则显示用户名。
- `contacts[].peerIps`：对端信令携带的真实 IP 数组（连接建立时写入）；`detectPeerIp` 在 `getStats()` 拿到 `*.local`/空时回退用它显示，并置 `ipType='signal'`。
- `contacts[].ipType`：对端地址来源，`host`/`prflx`（直连）/`srflx`（STUN 辅助）/`signal`（信令回退）。
- `messages[].dir`：`'in'` / `'out'` / `'sys'`（系统提示）；消息体为 `text`（文字）或 `file`（文件元数据）。
- `messages[].file`：文件消息元数据 `{fid,name,size}`，**不含文件内容**。
- `unread`：各联系人未读消息数；选中该联系人时清零。
- `settings`：v4 起仅直连模式；STUN 辅助现始终启用（代码常量 `DEFAULT_STUN_SERVERS`），无运行时开关，历史 `stunEnabled`/`stunUserSet` 字段已弃用忽略。

### 3.2 运行时状态（非持久化）

| 变量 | 说明 |
|------|------|
| `store` | 加载自 localStorage 的全局数据对象 |
| `currentId` | 当前选中联系人 id |
| `pendingPC` | 握手中的 `RTCPeerConnection` |
| `pendingPeerIps` | 解析对端连接码时暂存其真实 IP（`finalizeChannel` 写入 `contact.peerIps` 后清空） |
| `connections` | `Map<contactId, channel>`，已确认身份的活跃连接 |
| `channelMap` | `Map<channel, {pc, contactId|null, incomingFile?}>`，通道→连接信息反查 |
| `fileTransfers` | `Map<fid, {received,size,dir,contactId,name}>`，文件传输进度（出/入共用） |
| `fileUrls` | `Map<fid, objectURL>`，接收文件下载链接（运行时，不持久化） |
| `revivable` / `autoReviveTimers` | 断线恢复：存活 PC 缓存 / 自动恢复定时器 |
| `onboarding` / `exitAllowed` | 引导态标志 / 退出确认放行标志 |

## 4. 模块设计

### 4.1 WebRTC 层

- `newPC()`：创建 `RTCPeerConnection`，`iceServers` 始终填入 `DEFAULT_STUN_SERVERS`（国内公共 STUN + Cloudflare STUN / Google STUN 补充 IPv6），收集 `srflx` 候选绕过 mDNS。
- `waitIceComplete(pc)`：Promise，等 `iceGatheringState==='complete'`，带 5 秒兜底超时。
- `bindChannel(channel, pc, knownPeerId, knownPeerName)`：绑定通道事件（open/message/close/error）与 ICE 状态监听。
- `finalizeChannel(channel, peerId, peerName)`：身份确认后登记连接、创建/匹配联系人、写入 `pendingPeerIps`→`contact.peerIps`、探测对端 IP、切换 UI。
- `detectPeerIp(pc, contactId)`：通过 `pc.getStats()` 读取选中的 candidate-pair 解析对端地址；若为 `*.local`/空则回退用 `contact.peerIps` 并置 `ipType='signal'`。
- `connectDiagnose(pc)`：STUN 始终启用，根据 `hasRealHostCandidate(pc)` / 对端 IP 返回场景化诊断文案，供连接看门狗超时提示。

### 4.2 消息协议（DataChannel 传输 JSON 控制流 + ArrayBuffer 数据流）

JSON 控制消息（字符串）与二进制分块（ArrayBuffer）共用同一 DataChannel，`channel.binaryType='arraybuffer'`。

| type | 字段 | 说明 |
|------|------|------|
| `hello` | `identity` | 连接建立后互发，交换身份；已连接时再次发送表示**改名同步**（对端仅更新 `peerName`，不重走连接流程） |
| `msg` | `ts, text` | 聊天消息 |
| `file-meta` | `fid, name, size, mime` | 文件传输开始，声明元数据 |
| `file-end` | `fid` | 文件传输结束，接收方组装 Blob |
| `bye` | — | 主动断开通知 |

文件内容以 **ArrayBuffer 二进制分块**（16KB/块）紧随 `file-meta` 之后连续发送，`file-end` 标志完成。身份未确认（`contactId` 为 null）前，业务消息被丢弃。

### 4.3 存储层

- `loadStore()` / `saveStore()`：读写 localStorage，带 try/catch 容错；加载时迁移 contact 字段（补 `peerName`/`nameSet`）。
- 版本迁移：见 §6。
- `exportJSON()`：移动端优先 `navigator.share({files})` 弹系统分享菜单，回退 `<a download>` 下载 `p2pchat-backup-YYYYMMDD.json`。
- `importJSON()`：`<input type=file>` 读取，合并/覆盖后写入并刷新 UI；引导态导入成功后自动关闭引导。
- `boot()`：启动入口，无数据时显示引导（`dlgOnboard`）。
- `logoutAccount()` / `doLogout(backup)`：退出账号，清除 localStorage 并回引导；`backup=true` 时先 `await exportJSON()`。

### 4.4 本机地址探测

`collectMyIps()`：核心收集函数，创建临时 `RTCPeerConnection`（启用 `DEFAULT_STUN_SERVERS`），收集候选返回 `{host4,host6,mdns,srflx}`。

- `refreshMyIp()`：调用 `collectMyIps()` 后渲染本机地址面板。
- `extractIpsFromPc(pc)`：从握手 PC 已收集完成的 `localDescription` 中提取本机真实 IP（host + srflx，排除 `*.local`）。**复用握手 PC 已收集的候选**，避免为生成连接码 `ips` 字段再开临时 PC 做 STUN 收集（省一次网络往返）。
- `host` 候选 → 本机地址（IPv4/IPv6）；`*.local` → mDNS 混淆名；`srflx` → STUN 反射的公网地址。
- 渲染：本机真实 host IP 被 mDNS 全部隐藏（`host4`/`host6` 均空）且有 `srflx` 时，顶部标注「本机真实 IP 被 mDNS 隐藏，以下为 STUN 反射获取的公网地址」，srflx 行标签为「STUN」。

`fe80::` 开头标注「链路本地」。仅显示本机地址。

### 4.5 UI 渲染

- `renderAll()` / `renderContacts()` / `renderChat()` / `renderTopbar()` / `renderMessages()`：分层渲染。
- `contactDisplayText/Html(c)`：显示名规则——有备注显示「备注（用户名）」，否则显示用户名。
- `updateMobileView()`：根据 `currentId` 在 `#app` 上切换 `show-chat` 类，驱动移动端滑入式视图。
- 未读徽章：`renderContacts` 中 `store.unread[id]>0` 显示红色数字徽章，`selectContact` 清零。
- 对话框：连接向导、联系人详情、设置、首次引导（`dlgOnboard`）、操作提示（`dlgOnboardTips`）、退出确认（`dlgLogout`/`dlgExitConfirm`），均为 overlay 模态。

### 4.6 文件传输

- `sendFile(file)`：`file-meta` → 按 16KB `file.slice().arrayBuffer()` 分块发送 → `file-end`。`channel.bufferedAmount` 超 8MB 时等待 `bufferedamountlow` 事件做背压。
- `startReceiveFile()` / `finishReceiveFile()`：在 `channelMap` 条目的 `incomingFile` 上累积分块，完成后 `new Blob(chunks)` 生成 objectURL 存入 `fileUrls`。
- `renderFileCardInto()` / `updateFileProgress()`：文件卡片实时渲染进度条；传输中显示百分比，完成后接收方显示「下载」、发送方显示「已发送」。
- **文件内容仅存内存**：`fileUrls` 的 Blob 不持久化，刷新后失效；`store.messages` 仅存 `{fid,name,size}` 元数据。

## 5. 响应式布局

- 桌面端（>680px）：侧栏 300px + 主区 flex，双栏。
- 移动端（≤680px）：
  - `#app` 改为纵向；`#main` 绝对定位、`translateX(100%)` 隐藏；
  - 选中联系人时 `#app.show-chat #main` 滑入，侧栏隐藏；
  - 顶栏显示「‹」返回按钮；
  - 模态对话框改为底部抽屉式。
- **返回键分层拦截**（`history.pushState` + `popstate`）：
  - `boot` 注入根历史项 `{root}`；`selectContact` 注入 `{chat}`。
  - `popstate`：`currentId` 存在 → `goBack()` 回列表；已在列表 → 弹「退出 P2PChat？」确认（`dlgExitConfirm`），避免多次返回误退出。
  - 确认退出设 `exitAllowed=true` 放行 `history.back()`；取消则重新 pushState 根项继续拦截。

## 6. 版本迁移

`store.version` 用于数据格式升级：

| 版本 | 变更 |
|------|------|
| 1 | 初始版本，默认启用 STUN |
| 2 | 默认改为直连模式（禁用 STUN） |
| 3 | STUN 列表替换为国内可达服务器 |
| 4 | 彻底移除 STUN/TURN，仅保留直连；忽略历史 STUN 配置 |
| 4+ | 不升 version：STUN 辅助改为始终启用（代码常量 `DEFAULT_STUN_SERVERS`），历史 `stunEnabled`/`stunUserSet` 字段弃用忽略（见 §1.4） |

迁移逻辑同时存在于 `loadStore()`（启动加载）与 `importJSON()`（导入备份）。v4 起统一置 `version=4` 并忽略任何历史 STUN 配置；历史 `stunEnabled`/`stunUserSet` 字段不再读取（STUN 始终启用）。此外 `loadStore` 对 contact 做字段迁移：补 `nameSet`（默认 false）与 `peerName`（有备注则留空待连接同步，无备注则继承旧 `name`）；`peerIps` 为连接后按需写入的可选字段，旧数据缺失不影响。

## 7. 安全模型

### 7.1 传输安全
DataChannel 强制使用 DTLS。SDP 中的 DTLS 指纹在握手时由浏览器校验，所有数据端到端加密。仅直连模式下流量纯 P2P，不经过任何中转。

### 7.2 信令安全
连接码含 DTLS 指纹与会话凭证。本程序能防**被动窃听**，但**不能单独防主动中间人**：若攻击者能在不可信信道上篡改连接码，可替换为自身码进行转发。缓解措施：
- 通过可信渠道交换连接码；
- 或与对方口头核对一段短指纹（本程序未实现指纹显示，可作为扩展点）。

### 7.3 本地存储
`localStorage` 与导出 JSON 均为**明文落盘**，传输加密不覆盖本机存储。建议妥善保管导出文件。

## 8. 已知限制与扩展方向

| 限制 | 说明 | 可能扩展 |
|------|------|----------|
| 无法自动重连 | SDP 每次临时生成 | 引入轻量信令服务器实现「输入 ID 即连」 |
| 跨 NAT 不同网络无法直连 | STUN 仅获取反射地址，不能穿越对称型 NAT | 需引入 TURN 中继或信令服务器 |
| mDNS 混淆 | Chrome 默认将 host 候选改写为 `*.local`；较新 Chrome 已移除关闭 flag | 已通过 STUN 始终启用 srflx 候选绕过（见 §1.4）；本机真实 IP 被隐藏时显示 STUN 反射地址 |
| 文件不持久化 | 文件内容仅存内存，刷新后下载链接失效，仅保留元数据 | 用 IndexedDB 存储接收到的文件，刷新后可重建下载链接 |
| 无音视频传输 | 仅文本与文件 | 扩展 getUserMedia / MediaRecorder 音视频流 |
| 无群聊 | 仅一对一 | 需引入 mesh 或 SFU 架构 |
| 无指纹核对 | 信令防 MITM 依赖信道可信 | UI 展示 DTLS 指纹供人工核对 |

## 9. 浏览器兼容性

主测 Chrome / Edge（Chromium 内核），兼顾 Firefox。需支持 WebRTC DataChannel、`localStorage`、`RTCPeerConnection.getStats()`、`File.slice().arrayBuffer()`。`file://` 协议下均可运行；剪贴板复制带 `execCommand` 回退以兼容非安全上下文；移动端导出优先 Web Share API（`navigator.share({files})`），不支持时回退 `<a download>`。
